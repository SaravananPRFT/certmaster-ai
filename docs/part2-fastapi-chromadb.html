Dependency Injection: .NET vs FastAPI

.NET — IServiceCollection

// Program.cs
builder.Services
  .AddSingleton<IQuestionGenerator,
              QuestionGenerator>()
  .AddSingleton<IRetriever,
              AzureSearchRetriever>();

// Controller
public class QuestionController
{
    private readonly IQuestionGenerator _gen;
    public QuestionController(IQuestionGenerator gen)
        => _gen = gen;

    [HttpPost]
    public async Task<IActionResult> Generate(
        QuestionRequest req)
        => Ok(await _gen.Generate(req));
}

FastAPI — Depends()

# deps.py — factory functions
def get_generator() -> QuestionGenerator:
    return generator  # module-level singleton

# questions.py — router handler
@router.post("/generate")
async def generate_question(
    req: QuestionGenerationRequest,   # Pydantic body
    gen: QuestionGenerator = Depends(
        get_generator                    # DI injected
    ),
):
    q = await gen.generate_question(req)
    if not q:
        raise HTTPException(503)
    return q
In your project, generator = QuestionGenerator() is created at module load time (generator.py:441) — equivalent to AddSingleton. The Depends() call injects it per-request without re-creating it. This is the Python idiom for singleton DI.

How Components Communicate

questions.py (router — thin, no logic) │ │ Depends(get_generator) ← Python DI wiring │ ▼ generator.py (QuestionGenerator — orchestrator) │ ├── await retriever.retrieve() ← async I/O call, non-blocking │ │ │ ├── AzureSearchRetriever ← tries Azure AI Search first │ │ └── httpx.AsyncClient.post(search_url) │ │ │ └── ChromaRetriever ← fallback (chroma_retriever.py) │ └── collection.query(query_embeddings=[...]) │ ├── build_generation_prompt() ← pure function, no I/O, instant │ (prompts.py:162) │ └── await _llm_generate() ← async HTTP, ~1-3s latency │ ├── AsyncAzureOpenAI ← chat.completions.create() ├── AsyncOpenAI (Portkey) ← chat.completions.create() └── AsyncAnthropic ← messages.create()
Why async def matters: When FastAPI awaits retriever.retrieve(), the thread is released back to the event loop. The server can handle other incoming requests while waiting for Azure AI Search to respond. This is identical to async Task in C# — non-blocking I/O on a single thread. For an AI service that spends most time waiting on external APIs, this means hundreds of concurrent requests on one CPU core.

Section 5 — ChromaDB Architecture

ChromaDB is an embedded vector database — it runs inside your Python process with no separate server. Think of it as SQLite but for vectors: a folder on disk, fully queryable, zero infrastructure cost.

Internal Data Model

ChromaDB PersistentClient (path: ./chroma_db) │ ├── Collection: certmaster_ai_102 ← "Table" for AI-102 content │ │ │ ├── Segment: HNSW Vector Index ← The search structure (fast ANN) │ │ └── Graph of vectors, each connected to nearby vectors by cosine similarity │ │ └── Configured: hnsw:space = "cosine" (chroma_retriever.py:92) │ │ │ ├── Segment: Metadata Store ← SQLite under the hood │ │ └── chunk_id → {title, url, exam_code, chunk_index} │ │ │ └── Segment: Document Store ← Raw text strings │ └── chunk_id → "Key phrase extraction identifies..." │ ├── Collection: certmaster_az_104 ├── Collection: certmaster_az_305 ├── Collection: certmaster_gh_300 ├── Collection: certmaster_ab_100 ├── Collection: certmaster_ai_103 └── Collection: certmaster_ai_901 Collection naming: _coll_name(exam_code) → "AI-102" becomes "certmaster_ai_102" (chroma_retriever.py:11)

HNSW Explained — The Multi-Floor Building Analogy

HNSW = Hierarchical Navigable Small World Imagine a multi-floor building: Layer 2 (top): * ─────────── * ← few nodes, long jumps \ / Layer 1 (mid): * ─── * ─── * ─── * ← more nodes, medium jumps | | Layer 0 (base): ALL nodes (every chunk you indexed) When you search for a query vector: 1. Enter at the TOP layer with a random starting node 2. Walk GREEDILY: at each step, move to the neighbor nearest your query 3. When stuck (no neighbor is closer), DROP DOWN a layer 4. Repeat from step 2 on the lower layer 5. At Layer 0 (base), collect the K nearest neighbors Why FAST? You skip 99% of the graph — only visit a tiny path Why APPROX? You might miss the absolute best match (greedy walk) Why GOOD? For RAG, "very similar" is as useful as "most similar" Performance: Linear scan (exact): O(n) — checks every vector HNSW (approximate): O(log n) — traverses the graph hierarchy

Cosine Similarity vs Cosine Distance

ChromaDB with hnsw:space="cosine" returns DISTANCES (0 to 2): distance = 0.0 → identical vectors (perfect match) distance = 1.0 → orthogonal (completely unrelated) distance = 2.0 → opposite meaning Your code converts to similarity (chroma_retriever.py:60): score = max(0.0, 1.0 - distance) distance = 0.08 → score = 0.92 (excellent match) distance = 0.35 → score = 0.65 (decent match) distance = 0.70 → score = 0.30 (weak match) 2D Illustration (simplified from 3072D reality): Vector Space: "key phrase" embedding ● ↖ 8° angle (score ≈ 0.99) ● ← your query: "extract key phrases" ↙ 45° angle (score ≈ 0.71) "speech-to-text" embedding ●

Insert Operation

chroma_retriever.py : index_chunks() — lines 89–113
# Step 1: Get or create the collection for this exam
client = self._get_client()              # lazy-init PersistentClient
collection = client.get_or_create_collection(
    name=_coll_name(exam_code),           # "certmaster_ai_102"
    metadata={"hnsw:space": "cosine"},    # distance metric for HNSW
)

# Step 2: Upsert chunks (insert if new, update if chunk_id exists)
collection.upsert(
    ids=[c["chunk_id"] for c in chunks],         # primary keys
    documents=[c["content"] for c in chunks],     # raw text
    embeddings=[c["embedding"] for c in chunks],   # 3072-float vectors
    metadatas=[                                        # filterable metadata
        {
            "title":       c.get("title", ""),
            "url":         c.get("url", ""),
            "exam_code":   exam_code,
            "chunk_index": c.get("chunk_index", 0),
            "chunk_id":    c["chunk_id"],
        }
        for c in chunks
    ],
)
# ChromaDB internally:
# 1. Stores documents in Document Store
# 2. Stores metadatas in SQLite Metadata Store
# 3. Inserts embeddings into HNSW graph (re-builds incrementally)

Query Operation

chroma_retriever.py : retrieve() — lines 43–67
# Step 1: Generate query embedding using same model as ingestion
query_vec = embedder.embed(query)      # must use SAME model as ingestion!

# Step 2: Similarity search in ChromaDB
n = min(top_k, collection.count())    # can't request more than we have
results = collection.query(
    query_embeddings=[query_vec],         # [[0.045, -0.388, ...]]
    n_results=n,                          # top-K (default 5)
    include=["documents", "metadatas", "distances"],
)

# Step 3: Convert results to standard chunk dicts
chunks = []
for i, doc in enumerate(results["documents"][0]):
    meta     = results["metadatas"][0][i]
    distance = results["distances"][0][i]
    score    = max(0.0, 1.0 - distance)   # cosine distance → similarity
    chunks.append({
        "doc_id":  meta.get("chunk_id", f"chroma-{exam_code}-{i}"),
        "content": doc,
        "title":   meta.get("title", ""),
        "url":     meta.get("url", ""),
        "score":   score,
    })

What ChromaDB Does Internally During query()

1. Receive query_vec = [0.045, -0.388, 0.712, ...] 2. Enter HNSW graph at top layer Walk greedily toward query_vec using cosine distance 3. Drop to base layer Collect 5 nearest stored vectors 4. Fetch corresponding documents from Document Store Fetch corresponding metadata from SQLite Metadata Store 5. Return: results["documents"][0] → ["Key phrase extraction...", "NER identifies...", ...] results["metadatas"][0] → [{"title":"Azure AI Language","url":"...","exam_code":"AI-102"}, ...] results["distances"][0] → [0.08, 0.15, 0.22, 0.31, 0.44] ↑ closest ↑ farthest of top-5 6. Your code converts: score = 1.0 - distance [0.08, 0.15, 0.22, 0.31, 0.44] → [0.92, 0.85, 0.78, 0.69, 0.56]
Critical requirement: The embedding model used at query time must be the same model used at ingestion time. Both must project text into the same vector space for similarity to be meaningful. In your project: text-embedding-3-large (Azure OpenAI, 3072 dims) for production, nomic-embed-text (Ollama, 768 dims) for local dev. Never mix them — the vectors live in different spaces.
