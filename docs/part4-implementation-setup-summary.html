Section 9 — Local Development Setup

The entire stack can run on your laptop with zero cloud services. ChromaDB replaces Azure AI Search, Ollama replaces Azure OpenAI. The switchover to Azure is a config change only — no code changes.

Step-by-Step Setup

Terminal — complete local setup
# ─── 1. Install UV (Python package manager — Rust-based, 10-100x faster than pip) ───
curl -LsSf https://astral.sh/uv/install.sh | sh
# Windows PowerShell: irm https://astral.sh/uv/install.ps1 | iex

# ─── 2. Create virtual environment and install ALL dependencies ───
cd CertMasterAI/backend
uv sync                         # reads pyproject.toml, installs everything
                                # equivalent to: dotnet restore
                                # creates .venv/ automatically

# ─── 3. Install Ollama (local LLM runtime) ───
# Download from https://ollama.com, then:
ollama pull llama3.2:3b         # small LLM for generation (~2GB)
ollama pull nomic-embed-text    # embedding model (768-dim, ~274MB)
ollama serve                    # starts on http://localhost:11434

# ─── 4. Create .env file for local dev ───
cat > .env << 'EOF'
CHROMA_DB_PATH=./chroma_db
EMBEDDING_MODEL=nomic-embed-text
OLLAMA_BASE_URL=http://localhost:11434
# Leave Azure keys empty — code falls back to Chroma + Ollama
AZURE_OPENAI_KEY=
AZURE_OPENAI_ENDPOINT=
AZURE_SEARCH_ENDPOINT=
AZURE_SEARCH_KEY=
MIN_GROUNDING_SCORE=0.75
MIN_CITATION_COVERAGE=0.60
TOP_K_RETRIEVAL=5
EOF

# ─── 5. Start FastAPI ───
uv run uvicorn app.main:app --reload --port 8000
# equivalent to: dotnet run
# --reload = hot-reload on file change (like dotnet watch run)
# visit http://localhost:8000/docs for auto-generated Swagger UI

# ─── 6. Ingest documents into ChromaDB (one-time) ───
uv run python scripts/ingest.py --exam AI-102 --backend chroma
# This: loads .txt files → chunks → embeds → upserts to ChromaDB

# ─── 7. Test ───
curl -X POST http://localhost:8000/api/v1/questions/generate \
     -H "Content-Type: application/json" \
     -d '{"exam_code": "AI-102", "difficulty": "Medium", "count": 1}'

Switching from Local to Azure — Config Change Only

Local .env (dev)

# Empty → uses ChromaDB + Ollama
AZURE_SEARCH_ENDPOINT=
AZURE_SEARCH_KEY=
AZURE_OPENAI_KEY=
AZURE_OPENAI_ENDPOINT=

# Local services active
CHROMA_DB_PATH=./chroma_db
OLLAMA_BASE_URL=http://localhost:11434

Production .env (Azure)

# Set → uses Azure AI Search + OpenAI
AZURE_SEARCH_ENDPOINT=https://certmaster.search.windows.net
AZURE_SEARCH_KEY=sk-...
AZURE_OPENAI_KEY=...
AZURE_OPENAI_ENDPOINT=https://certmaster.openai.azure.com
AZURE_OPENAI_DEPLOYMENT=gpt-4o
AZURE_OPENAI_EMBEDDING_DEPLOYMENT=text-embedding-3-large

# ChromaDB still present as fallback
CHROMA_DB_PATH=./chroma_db
Zero code changes. The Settings Pydantic BaseSettings class reads environment variables at startup. The retriever.py checks settings.AZURE_SEARCH_ENDPOINT — if it's set, Tier 1 (Azure AI Search) activates. If empty, it skips to Tier 2 (ChromaDB). This is the config-driven environment switching pattern — identical to how .NET's IConfiguration works with appsettings.Development.json vs appsettings.Production.json.

Key Takeaways for Technical Design Reviews

1

Why FastAPI?

Async HTTP serving + automatic Pydantic schema validation + auto-generated OpenAPI docs with essentially zero boilerplate. For an I/O-bound AI service that spends most of its time waiting on external APIs, async def + await means hundreds of concurrent requests on one thread — same as async Task in C#.

2

Why RAG?

LLMs hallucinate when answering from training memory. RAG converts the problem: instead of "what do you know about X?", the LLM answers "what does this context say about X?" Your grounding gate (grounding_score < 0.75 → drop) enforces this contract programmatically — every answer must cite its sources.

3

Why Two Vector Stores?

ChromaDB costs nothing and runs offline — perfect for development and CI. Azure AI Search costs money but provides hybrid + semantic search that measurably improves retrieval quality. The tiered retriever (Azure → Chroma → fallback) gives you the best of both: develop locally for free, deploy with full fidelity.

4

The Golden Rule of Chunking

A chunk must be small enough to be precise (only retrieved when relevant) and large enough to contain a complete idea. Overlap (~10%) ensures boundary sentences aren't lost. The chunk feeds directly into the prompt — if a chunk is too large, you waste context tokens; too small and you lose meaning.

5

Embeddings Are the Secret

Both query and every stored document are converted to the same vector space using the same model. Similarity search is then pure geometry: find stored vectors with the smallest angle to the query vector. Everything else — ChromaDB, Azure AI Search, HNSW — is infrastructure around this one idea. The model choice matters enormously: text-embedding-3-large (3072-dim) is far more capable than ada-002 (1536-dim).

6

Hybrid > Vector-Only for Technical Content

For general language, pure vector search is good enough. For precise technical content (exam questions involving "NSG", "RBAC", "SAS token"), BM25 keyword search catches what semantic search misses. Azure AI Search's hybrid mode + semantic reranker delivers the best of both — this is why it is your Tier 1 retriever.

MCP — Model Context Protocol

What is MCP? The Model Context Protocol is an open standard (introduced by Anthropic, late 2024) that defines how LLM-powered agents communicate with external tools, data sources, and services. Think of it as REST for AI agents — just as REST standardized how web services talk to each other, MCP standardizes how LLMs call external capabilities.

Without MCP: Each AI app writes custom glue code to connect to each tool. GitHub connector → custom code Database connector → different custom code Search connector → yet another custom code 100 tools = 100 different integration patterns With MCP: LLM (Claude, GPT-4o, etc.) │ │ MCP Protocol (standardized JSON-RPC) │ ┌────┴────────────────────────────────────────────┐ │ MCP Servers (each exposes tools + resources) │ │ │ │ ● filesystem MCP server (read/write files) │ │ ● GitHub MCP server (repos, PRs, issues) │ │ ● PostgreSQL MCP server (query DB) │ │ ● Azure AI Search MCP (vector search) │ │ ● CertMasterAI MCP (exam questions) │ └──────────────────────────────────────────────────┘ Any MCP-compatible LLM can use any MCP server. No custom integration code.

How MCP extends RAG: In a standard RAG pipeline, retrieval is hard-coded — the system always queries the same vector DB with the same strategy. With MCP, the LLM can decide which tool to call: "I need current information → call the live web search MCP server; I need document history → call the Azure AI Search MCP server; I need to run a calculation → call the code execution MCP server." This turns RAG from a fixed pipeline into a dynamic, agent-driven retrieval system.

In CertMasterAI's context: An MCP server wrapping your FastAPI backend would allow any MCP-compatible client (Claude Desktop, GitHub Copilot, VS Code Copilot) to call generate_question(exam_code, difficulty) as a tool — without any custom API integration. The MCP server handles the protocol translation.

Interview answer for "What is MCP?": MCP is to AI agents what REST is to web services — a standardized protocol that lets any LLM call any tool without custom glue code. It separates the "what to call" decision (made by the LLM) from the "how to call it" implementation (handled by MCP servers). It enables composable, interoperable agentic systems.
